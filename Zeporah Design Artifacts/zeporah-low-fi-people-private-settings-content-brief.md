# Zeporah Low-Fidelity People, Private Information, and Settings Content Brief

This document completes the frame-by-frame low-fidelity content briefs for Zeporah by covering the remaining core product sections: People and permissions, Private information, and Settings and trust.[cite:9][cite:16][cite:17]

Together with the onboarding, home, tasks, and support briefs, this document completes the written content and layout blueprint for the full low-fidelity wireframe system.[cite:26]

## Usage rules

Each frame should include an annotation block with purpose, role, primary action, trust cues, role restrictions, and next branches.[cite:26]

These sections should emphasize control, clarity, and recoverability. None of them should feel administrative for its own sake; each should reinforce that Zeporah helps families coordinate carefully while staying in control of access and private information.[cite:16][cite:9]

## People and permissions

### LF-26 People list

**Purpose:** Show who is currently involved, who is pending, and what level of access each person has.[cite:9]

**Frame structure:**
- Header with title and invite action.[cite:9]
- Short helper text: “You choose who can help and what they can see.”[cite:9]
- Section 1: People in this space.[cite:9]
- Section 2: Pending invitations.[cite:9]
- Each person row should include:
  - Name.[cite:9]
  - Role badge.[cite:9]
  - Access summary line.[cite:9]
  - Status, such as Active or Pending.[cite:9]
- Primary CTA: Invite someone.[cite:9]
- Row action: Open person detail.[cite:9]

**Trust cue:**
- “Access can be changed later.”[cite:9]

### LF-27 Person detail

**Purpose:** Let the coordinator review one person’s role and visibility clearly before making changes.[cite:9]

**Frame structure:**
- Header with back to People list.[cite:9]
- Person identity block: name, role, status.[cite:9]
- Access summary card: what they can view, update, or help with.[cite:9]
- Shared areas list, such as tasks, updates, contacts, or selected documents.[cite:9]
- Optional recent activity summary at a very high level.[cite:9]
- Primary CTA: Change access.[cite:9]
- Secondary CTA: Remove access.[cite:9]
- Optional link: Resend invitation, if pending.[cite:9]

**Trust cue:**
- “Changes take effect from this point forward.”[cite:9]

### LF-28 Change access

**Purpose:** Edit one person’s permissions using plain language rather than technical access-control terms.[cite:9]

**Frame structure:**
- Header with back and save path.[cite:9]
- Main headline: “Choose what [Name] can see and do.”[cite:9]
- Permission blocks by content type:
  - Tasks.[cite:9]
  - Updates.[cite:9]
  - Contacts.[cite:9]
  - Documents.[cite:9]
  - Notes, if ever shareable.[cite:9]
- Simple permission choices such as Can view, Can update, Can complete assigned items, No access.[cite:9]
- Optional role adjustment area.[cite:9]
- Primary CTA: Review changes.[cite:9]
- Secondary CTA: Cancel.[cite:9]

**Trust cue:**
- “Private notes and other protected areas stay hidden unless you choose otherwise.”[cite:9][cite:12]

### LF-29 Permission review

**Purpose:** Confirm access changes before they go live.[cite:9]

**Frame structure:**
- Header with back.[cite:9]
- Main headline: “Review these access changes.”[cite:9]
- Comparison table:
  - Current access.[cite:9]
  - New access.[cite:9]
- Optional note about whether the person will be notified.[cite:9]
- Primary CTA: Confirm changes.[cite:9]
- Secondary CTA: Edit access.[cite:9]

**Trust cue:**
- “This review helps prevent accidental over-sharing.”[cite:9]

### LF-30 Remove access

**Purpose:** Revoke access with enough warning to avoid accidental removal but without making it hard to protect the space.[cite:9]

**Frame structure:**
- Header with back.[cite:9]
- Main headline: “Remove access for [Name]?”[cite:9]
- Short warning paragraph explaining what access ends and what remains in the shared record.[cite:9]
- Optional reassignment prompt for outstanding tasks.[cite:9]
- Primary CTA: Remove access.[cite:9]
- Secondary CTA: Cancel.[cite:9]

**Trust cue:**
- “They will no longer be able to open this space after removal.”[cite:9]

### LF-31 Pending invite detail

**Purpose:** Manage an invitation that has not yet been accepted.[cite:9]

**Frame structure:**
- Header with back.[cite:9]
- Invite status block: recipient, role offered, sent date, expiration if used.[cite:9]
- Access summary preview.[cite:9]
- Actions:
  - Resend invitation.[cite:9]
  - Change access before acceptance.[cite:9]
  - Cancel invitation.[cite:9]
- Primary CTA: Resend invitation or Edit access, depending state.[cite:9]

**Trust cue:**
- “No access is active until the invitation is accepted.”[cite:9]

## Private information

### LF-40 Private information hub

**Purpose:** Give the user a single place to hold the important practical information connected to the family situation.[cite:17][cite:16]

**Frame structure:**
- Header with title and add action.[cite:17]
- Intro text: “Keep important details here so they are easier to find later.”[cite:17]
- Card grid or list linking to:
  - Documents.[cite:17]
  - Notes.[cite:9]
  - Contacts.[cite:17]
  - Decision log.[cite:17][cite:16]
  - Expense ledger.[cite:17]
- Each card includes item count or placeholder state.[cite:17]
- Primary CTA: Open selected section.[cite:17]

**Trust cue:**
- Each section card displays default visibility state such as Private or Shared with selected people.[cite:9]

### LF-41 Documents list

**Purpose:** Organize important files without making the user search across different product areas.[cite:17][cite:9]

**Frame structure:**
- Header with title and add/upload action.[cite:9]
- Optional filters: All, Private, Shared, Recent.[cite:9]
- Document rows include:
  - File name.[cite:9]
  - Category or tag.[cite:17]
  - Date added.[cite:9]
  - Visibility label.[cite:9]
- Empty state: “Keep forms, records, and important files here.”[cite:17]
- Primary CTA: Open document detail.[cite:9]
- Secondary CTA: Add document.[cite:9]

### LF-42 Document detail

**Purpose:** Show one file with enough context to manage access and related work.[cite:9]

**Frame structure:**
- Header with back.[cite:9]
- File title and category.[cite:9]
- Metadata line: added by, date, visibility.[cite:9]
- Optional short description or note.[cite:9]
- Related items section: linked task, contact, or decision if relevant.[cite:17]
- Action row:
  - Change visibility.[cite:9]
  - Link to a task.[cite:17]
  - Archive or remove.[cite:9]
- Primary CTA: Update visibility or open related action.[cite:9]

**Trust cue:**
- “Opening a document does not share it.”[cite:9][cite:12]

### LF-43 Private notes

**Purpose:** Give the user a safe place for personal observations and reminders that are not automatically turned into shared updates.[cite:9]

**Frame structure:**
- Header with title and add-note action.[cite:9]
- Intro line: “Private notes stay private unless you share them intentionally.”[cite:9]
- Note rows with title or first line, date, and privacy label.[cite:9]
- Empty state: “Write down details you want to remember later.”[cite:9]
- Primary CTA: Open or add note.[cite:9]

### LF-44 Contacts directory

**Purpose:** Keep important people and organizations together in one findable list.[cite:17]

**Frame structure:**
- Header with title and add-contact action.[cite:17]
- Filters or categories such as Family, Care team, Practical help, Services, Other.[cite:17][cite:9]
- Contact rows include:
  - Name.[cite:17]
  - Category.[cite:17]
  - Phone or email snippet.[cite:9]
  - Visibility label.[cite:9]
- Primary CTA: Open contact detail.[cite:17]
- Secondary CTA: Add contact.[cite:17]

**Trust cue:**
- “Contacts remain in your family space unless you choose to share them.”[cite:9]

### LF-45 Decision log

**Purpose:** Capture decisions so the family does not lose context or re-litigate details later.[cite:17][cite:16]

**Frame structure:**
- Header with title and add-decision action.[cite:17]
- Intro line: “Keep track of what was decided, by whom, and what happens next.”[cite:17][cite:16]
- Decision rows should include:
  - Decision title.[cite:17]
  - Date.[cite:17]
  - Owner or who confirmed it.[cite:16]
  - Next step, if any.[cite:17]
- Primary CTA: Open or add decision.[cite:17]

**Trust cue:**
- Visibility label shown on each row.[cite:9]

### LF-46 Expense ledger

**Purpose:** Track out-of-pocket costs and practical financial follow-up in a simple, non-accounting-heavy way.[cite:17]

**Frame structure:**
- Header with title and add-expense action.[cite:17]
- Intro line: “Track costs, reimbursements, or items to follow up on.”[cite:17]
- Expense rows include:
  - Item name.[cite:17]
  - Amount placeholder.[cite:17]
  - Status such as Paid, Pending, Reimbursable, Follow up.[cite:17]
  - Visibility label.[cite:9]
- Optional total or grouped summary block.[cite:17]
- Primary CTA: Open or add expense.[cite:17]

**Trust cue:**
- “This is for tracking and organization, not financial or tax advice.”[cite:17][cite:9]

## Settings and trust

### LF-58 Settings home

**Purpose:** Give the user a clean index of control areas without turning settings into a dense admin page.[cite:9][cite:16]

**Frame structure:**
- Header with title.[cite:9]
- Intro line: “Manage privacy, reminders, support preferences, and connections here.”[cite:9]
- Settings list or grouped cards linking to:
  - Privacy defaults.[cite:9]
  - Support and recommendation preferences.[cite:12][cite:9]
  - Reminder preferences.[cite:9]
  - Partner connection settings.[cite:9]
  - Audit history summary.[cite:9][cite:12]
- Primary CTA: Open selected settings area.[cite:9]

### LF-59 Privacy defaults

**Purpose:** Let the coordinator change how new content behaves before it is shared.[cite:9]

**Frame structure:**
- Header with back and save path.[cite:9]
- Main headline: “Default privacy for new items.”[cite:9]
- Settings blocks for tasks, updates, contacts, documents, notes, and support drafts.[cite:9]
- Explanation beneath each setting in plain language.[cite:9]
- Primary CTA: Save changes.[cite:9]
- Secondary CTA: Restore recommended defaults.[cite:9]

**Trust cue:**
- “You can still change visibility item by item later.”[cite:9]

### LF-60 Support and recommendation preferences

**Purpose:** Control how support options are matched and displayed.[cite:12][cite:9]

**Frame structure:**
- Header with back and save path.[cite:9]
- Main headline: “Support preferences.”[cite:9]
- Controls for:
  - Local or virtual preference.[cite:9]
  - Preferred language.[cite:9]
  - Faith or spiritual preference, optional.[cite:12]
  - Cost preference.[cite:12][cite:9]
  - Accessibility preference.[cite:12][cite:9]
  - Turn suggestions off, if allowed.[cite:9]
- Primary CTA: Save preferences.[cite:9]

**Trust cue:**
- “These preferences do not contact anyone or share your details.”[cite:12][cite:9]

### LF-61 Reminder preferences

**Purpose:** Let users control the tone and timing of reminders so the app stays supportive rather than nagging.[cite:9][cite:12]

**Frame structure:**
- Header with back and save path.[cite:9]
- Main headline: “Reminder preferences.”[cite:9]
- Controls for:
  - Essential only / Gentle reminders / No reminders.[cite:9][cite:12]
  - Quiet hours.[cite:9]
  - Email, text, or in-app if supported.[cite:9]
  - Return-later behavior for hidden or paused items.[cite:12]
- Primary CTA: Save preferences.[cite:9]

**Trust cue:**
- “Reminders use your settings and do not reveal private details.”[cite:9]

### LF-62 Partner connection settings

**Purpose:** Let the user manage sponsor-related support routing without confusing it with workspace membership or visibility.[cite:9]

**Frame structure:**
- Header with back and save path.[cite:9]
- Main headline: “Partner support connection.”[cite:9]
- Status card: connected / not active / private mode.[cite:9]
- Explanation block:
  - What remains private.[cite:9]
  - What may be shared only during a reviewed request.[cite:12][cite:9]
- Toggle or choice control:
  - Keep support connection available.[cite:9]
  - Use privately for now.[cite:9]
- Primary CTA: Save setting.[cite:9]

**Trust cue:**
- “Turning this on does not give a partner access to your workspace.”[cite:9]

### LF-63 Audit history summary

**Purpose:** Reinforce trust by showing major access and support events without exposing unnecessary private content.[cite:9][cite:12]

**Frame structure:**
- Header with back.[cite:9]
- Main headline: “Activity and trust history.”[cite:9]
- Event list may include:
  - Invitation sent or canceled.[cite:9]
  - Access changed.[cite:9]
  - Support request sent or withdrawn.[cite:12]
  - Partner connection setting changed.[cite:9]
- Each row should include date, event type, and short description.[cite:9][cite:12]
- Primary CTA: Open event detail if needed.[cite:9]

**Trust cue:**
- “This history shows important changes, not your private content.”[cite:9][cite:12]

## Review checklist

These sections should be considered ready for full low-fidelity integration when the following are true.[cite:26][cite:9][cite:12]

- Every people-management screen makes access scope legible before and after changes.[cite:9]
- Every private-information section clearly signals visibility state.[cite:9]
- Settings screens reinforce control without introducing legalistic complexity.[cite:9][cite:16]
- Audit and partner-related screens strengthen trust rather than raising new confusion.[cite:9][cite:12]
- The tone remains calm, practical, and respectful across administrative moments as well as support moments.[cite:16][cite:17]
